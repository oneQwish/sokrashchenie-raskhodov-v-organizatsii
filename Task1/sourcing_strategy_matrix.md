# Task 1. Матрица Sourcing Strategy (Buy vs Build) — VitaStore

Матрица построена по карте возможностей. Решение по каждой возможности принимается по трём правилам, в таком порядке:

1. Если функцию по закону или технически нельзя вынести из магазина — **In-house / On-Premise** (на стороне магазина, Edge).
2. Если у VitaStore уже есть своя работающая система — переносим её в облако как есть: **PaaS/IaaS (Migrate)**. Так решено для SAP ERP и Promo Engine. Покупать новую систему взамен работающей дороже, чем перенести.
3. Для остальных функций: стандартная функция, которая не отличает VitaStore от конкурентов, — **SaaS (Buy)**; функция, дающая конкурентное преимущество, — **PaaS (Build in Cloud)**.

Исключение — возможность «Интеграция приобретённых магазинов» (на карте выделена жёлтой шапкой). Сейчас она дорогая и ручная, поэтому окрашена красным. Но от неё зависит рост через M&A, поэтому по её подфункциям решение принимается отдельно: сервис переноса и сопоставления номенклатуры строим сами (языковую модель для него покупаем по API), подключение оборудования покупаем, выезд ИТ-бригады ликвидируем.

Кроме трёх моделей из задания используется пометка Retire: функция в целевой архитектуре исчезает вместе со своим дублем.

## Матрица

| Возможность (L2) | Heatmap | Решение | Правило | Обоснование |
|---|---|---|---|---|
| Расчёт с покупателем (касса), в том числе без связи | 🔴 | SaaS + Edge — Cloud POS | 3, 1 | Стандартная функция. Толстый клиент и сервер в каждом магазине — главная статья TCO. Данные для работы без связи хранятся на устройстве в магазине (INC-8402). |
| Приём оплаты картой (терминалы разных банков) | 🔴 | SaaS + Edge — драйверы оборудования в составе Cloud POS | 3, 1 | Каждому терминалу нужен свой драйвер (INC-8415: ARCUS-2, 3 недели разработки). Кассовые продукты поставляются с драйверами под основные протоколы (ARCUS-2, DualConnector, UPOS) за общим интерфейсом «оплатить / вернуть / сверить итоги». Драйверы работают на смарт-терминале в магазине, управляются из облака. |
| Фискализация чеков (ФН) | 🔴 | On-Premise | 1 | Фискальный накопитель по 54-ФЗ находится в ККТ в магазине. Вместо разнородных фискальных регистраторов — смарт-терминал со встроенным ФН. |
| Печать ценников | 🔴 дубль | SaaS — модуль Cloud POS | 3 | Сейчас ценник печатается по ценам из локальной БД и может расходиться с чеком. В целевом состоянии чек и ценник берут цену из одного центрального источника. |
| Программа лояльности | 🔴 дубль | SaaS | 3 | В купленных магазинах лояльность ведётся «в тетрадке», параллельно центральной. Ограничение при выборе поставщика: персональные данные участников хранятся в РФ (152-ФЗ). |
| Промоакции (Promo Engine) | стандартная | PaaS — перенос | 2 | Система есть и работает. Переносим на управляемые облачные сервисы без переписывания. |
| Smart Fulfillment, Click & Collect | 🟢 | PaaS — Build | 3 | Кейс называет это главным конкурентным преимуществом сети. Развиваем сами на облачной платформе. |
| Приёмка от локальных поставщиков | 🔴 дубль | SaaS — ЭДО + модуль приёмки Cloud POS | 3 | Сейчас это параллельный канал закупок в обход HQ. Приёмка переходит в общий контур, данные сразу попадают в SAP. |
| Товарный учёт, закупки, цены, финансы, кадры (SAP ERP) | стандартная | IaaS — перенос SAP в облако | 2 | SAP уже есть. Переносим на облачную инфраструктуру. Отдельный риск — поддержка вендора в РФ, он вне рамок кейса. |
| Учёт остатков в магазине (локальная БД) | 🔴 дубль | Retire | — | Остатки ведутся в одном месте, в SAP. Касса передаёт движения товара. Локальная БД уходит вместе с сервером. |
| Эталонный каталог товаров (НСИ) | стандартная | SaaS — MDM/PIM | 3 | Типовая задача. По этому каталогу сверяются штрихкоды при онбординге (Task 2). |
| Локальная номенклатура магазина | 🔴 дубль | Retire | — | Базу купленного магазина используем один раз при онбординге как источник штрихкодов и названий для сопоставления (Task 2). Все позиции привязываются к эталонному каталогу, локальная номенклатура уходит вместе со старой кассой. |
| Перенос и сопоставление номенклатуры при M&A | 🔴 | PaaS — Build + SaaS (языковая модель по API) | исключение | Готового продукта под процесс VitaStore (выгрузка старой базы → сверка штрихкода с каталогом → AI-сервис для позиций без совпадения → проверка товароведом) нет. Сервис онбординга строим сами поверх покупного каталога. Языковую модель для AI-сопоставления подключаем готовую, по API с оплатой за запросы. |

| Подключение платёжного оборудования | 🔴 | SaaS + Edge | исключение | То же решение, что для приёма оплаты картой. |
| Инкассация | 🔴 | SaaS — услуга банка + учёт в Cloud POS | 3 | Стандартная функция. |
| Расчёт премий продавцам | 🔴 дубль | IaaS — в SAP HR | 2 | Премии считаются локально, хотя зарплата уже в SAP HR. Данные продаж для расчёта берутся из Cloud POS. |
| Администрирование локальных серверов и лицензий | 🔴 | Retire | — | Уходит вместе с серверами. По кейсу на это сейчас тратится 40% ИТ-бюджета. |
| Поддержка касс и оборудования, service desk | 🔴 | SaaS + удалённое управление устройствами | 3 | Вместо выездов — удалённая диагностика и замена устройства курьером. |

## Итог

- SaaS (Buy): касса Cloud POS с драйверами оборудования, лояльность, эталонный каталог, языковая модель для AI-сопоставления, приёмка через ЭДО, ценники, инкассация, service desk.
- PaaS/IaaS: Smart Fulfillment и Click & Collect (Build), сервис сопоставления номенклатуры (Build), Promo Engine и SAP ERP (перенос).
- On-Premise (Edge): фискальный накопитель, драйверы оборудования, данные для работы кассы без связи. Серверов в магазине нет.
- Retire: локальные серверы, локальная БД остатков, локальная номенклатура, выезд бригады на подключение.
